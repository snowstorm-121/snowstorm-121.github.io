RetailFlow

让模型提出操作，让应用核验边界：在模拟零售业务中，追踪确认、提交与恢复。

问题航标

零售执行需要检查实际订单变化，不能只看回答是否流畅。模型可能选错工具、遗漏身份追问，或在用户改变需求后沿用旧确认；进程重启后，也需要判断写操作是否已经提交。

RetailFlow 是本地 CLI Agent 实验原型，基于 LangGraph、Ollama 与 τ2 retail 模拟环境，研究查询、取消与退货中的确认和恢复边界。不连接真实订单、支付或客服系统。

工程舱图

LangGraph 运行模型—工具循环，Ollama 接入本地 Qwen3 4B。模型选择工具和参数，应用负责协议、身份与订单所有权校验；用户脚本与评分器不参与模型规划。

confirm_action 不向模型暴露；模型不能通过 approved=true 替用户确认。更换订单、商品或原因都不能沿用旧提案。已提交操作先查回执，写入结果未知时不盲目重试；明确发生在执行前的只读临时故障最多重试一次。

SQLite 事务覆盖本地业务快照与执行回执，不覆盖业务、对话和模型请求的全局事务，也不是分布式 exactly-once 保证。实现采用自定义 SQLite 表，未接入 LangGraph 原生 SqliteSaver。

结论星屿

应用保护能约束部分副作用，无法替代模型正确规划与必要沟通。当前仅是实验性本地 CLI 与模拟业务，身份定位不是生产认证，尚无真实平台集成、生产负载、稳定性或全面提示注入防护结论。

项目基于 LangChain react-agent 模板和 τ2-bench retail 的数据、政策及业务方法。新增工作集中于本地模型接入、受控工具节点、身份与提案确认、SQLite 回执恢复及冻结派生评测；不代表从零自研 Agent 框架或全部订单规则。工程实现使用了 Codex 辅助。
